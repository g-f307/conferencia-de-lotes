O GitHub Flow

O primeiro fluxo profissional — simples e poderoso

O GitHub Flow é o fluxo de trabalho recomendado para iniciantes e para projetos com entrega contínua. É simples o suficiente para aprender em uma aula e profissional o suficiente para usar em empresas reais.

O GitHub Flow em 7 passos — cada tarefa começa com uma Issue e termina com um Merge

Por que começar pelo GitHub Flow e não pelo Git Flow?

✅
GitHub Flow — para iniciantes e CD

Apenas main + branches de feature. Simples, fácil de ensinar, usado amplamente em startups e open source. Uma regra: a main é sempre deployável.

⚠️
Git Flow — para contextos avançados

Branches develop, release, hotfix... Mais estruturado, porém mais complexo. Ensinar depois que o aluno já domina o GitHub Flow.

A regra de ouro do GitHub Flow

🧠
Tudo que está na main pode ser deployado a qualquer momento

Nenhum código vai direto para a main. Toda mudança vem via branch + Pull Request + revisão. Isso garante que a main sempre esteja estável e pronta para produção.

⌨

O vocabulário mínimo para participar do GitHub Flow

🔍 Fase 3 — Inspeção

git diffver o que mudou

🚨 Fase 4 — Situações especiais

git refloghistórico completo de movimentos

Execute esses comandos antes de qualquer coisa

Configure o Git uma vez por máquina: git config --global user.name "Seu Nome" e git config --global user.email "email@exemplo.com". Sem isso, seus commits não terão identidade.

Exercício 1 — Trabalhando com Issues

Toda alteração começa com uma justificativa

📋 Issue› 🌿 Branch› 💾 Commits› ⬆ Push› 🔀 PR› 👁 Review› ✅ Merge› 🗑 Deletar
🎯
Objetivo

Entender que uma branch nunca nasce "do nada". Cada branch está ligada a uma tarefa, melhoria ou correção rastreada por uma Issue.

Exercício 1

🧪 Criando o repositório e as Issues da sprint

1

Criar o repositório no GitHub

Um membro cria o repositório conferencia-lotes-qualidade no GitHub (privado) e convida os colegas como collaborators em Settings → Collaborators. Repositório privado é obrigatório — propriedade intelectual da LG (Convênio 005/2025).

2

Criar as Issues iniciais

Vá em Issues → New Issue e crie as 5 tarefas abaixo. Cada aluno deve escolher uma:

issues a criar no github
Issue #1:  "Implementar RN01–RN02: estrutura e campos obrigatórios"  → label: feature
Issue #2:  "Implementar RN03: verificar lote na base de referência"  → label: feature
Issue #3:  "Implementar RN04–RN05: status e normalização OK/NOK"     → label: feature
Issue #4:  "Implementar RN07: observação obrigatória em reprovado"   → label: feature
Issue #5:  "Gerar relatório de divergências em .xlsx"                → label: feature
3

Configurar cada Issue

Para cada Issue, preencha:

  • Title: título claro e direto
  • Description: o que deve ser feito e critérios de aceite
  • Assignees: quem vai resolver
  • Labels: feature, style, etc.
  • Milestone: "Sprint 1" (criar antes se não existir)
4

Verificar na aba Issues

Todos os membros devem conseguir ver as 5 Issues abertas na aba Issues do repositório. O painel de Issues é o quadro de trabalho da equipe.

Template de Issue bem escrita

markdown — exemplo de Issue #1
## O que precisa ser feito
Implementar a validação de estrutura (RN01) e campos obrigatórios (RN02) conforme PDD v0.2 seção 12.

## Critérios de aceite
- [ ] Função valida_estrutura() retorna erro se faltar alguma das 8 colunas
- [ ] Função valida_campos_obrigatorios() detecta campos vazios em lote_id, produto, linha, turno, status, responsavel, data
- [ ] Testes unitários com pytest cobrindo ao menos 3 casos de campo vazio
- [ ] Código em src/validacao.py, referenciando RN01 e RN02 nos docstrings
- [ ] README atualizado com instruções de execução

## Referências visuais
(Inserir print ou link de referência se houver)
💡
Aprendizado do exercício

Não se cria uma branch "do nada". Cada branch nasce de uma Issue que justifica e documenta a mudança. Isso rastreia o que foi feito, por quem e por quê — essencial em equipes.

03

Exercício 3 — Abrindo Pull Request

A porta de entrada do código na main

📋 Issue ✓› 🌿 Branch ✓› 💾 Commits ✓› ⬆ Push ✓› 🔀 PR› 👁 Review› ✅ Merge› 🗑 Deletar
🎯
Objetivo

Entender que o código nunca vai direto para a main. Toda mudança proposta chega via Pull Request, que é a oportunidade de revisar, discutir e melhorar antes de integrar.

Exercício 3

🧪 Abrindo o primeiro Pull Request

1

Entrar no repositório no GitHub

Após fazer o push da branch, o GitHub geralmente exibe um banner amarelo: "Compare & pull request". Clique nele. Se não aparecer, vá em Pull Requests → New Pull Request.

2

Verificar as branches

Confirme que está correto:

  • base: main (para onde o código vai entrar)
  • compare: feature/cabecalho (o que você está propondo)
3

Preencher o Pull Request

Use o template abaixo. Um PR bem descrito é revisado mais rápido e com mais qualidade:

markdown — descrição do PR
## O que foi feito?

- Adiciona src/validacao.py com valida_estrutura() e valida_campos_obrigatorios()
- Adicionado título principal com <h1>
- Incluído menu de navegação <nav> com 4 links
- Aplicado estilo CSS básico de cor e tipografia

## Issue relacionada

Closes #1

## Como testar?

1. Abrir o arquivo `index.html` no navegador
2. Verificar se o cabeçalho aparece no topo
3. Conferir se os links do menu estão visíveis e funcionais

## Checklist

- [x] Branch criada a partir da main atualizada
- [x] Nome da branch segue o padrão
- [x] Commit referencia a Issue (#1)
- [x] Sem arquivos desnecessários (.DS_Store, node_modules)
4

Configurar o PR

No painel lateral do PR:

  • Reviewers: adicionar o colega que vai revisar (rotação de duplas)
  • Assignees: você mesmo (quem criou o PR)
  • Labels: feature ou style
5

Clicar em "Create Pull Request"

O PR está aberto! Agora aguarde o colega fazer a revisão (Exercício 4).

🔗
O poder do "Closes #1"

Quando você escreve Closes #1 na descrição do PR, o GitHub vincula automaticamente o PR à Issue #1. Quando o PR for mergeado na main, a Issue é fechada automaticamente. Palavras aceitas: closes, fixes, resolves, close, fix, resolve.

Exercício 4 — Revisão de Pull Request

Melhorando o código antes de integrar

📋 Issue ✓› 🌿 Branch ✓› 💾 Commits ✓› ⬆ Push ✓› 🔀 PR ✓› 👁 Review› ✅ Merge› 🗑 Deletar
🎯
Objetivo

Aprender que um PR nunca é aprovado pelo próprio autor. A revisão por par melhora a qualidade, distribui o conhecimento e cria responsabilidade coletiva pelo código.

Dinâmica de duplas — quem revisa quem

Aluno Bfeature/secao-sobreAluno C (feature/secao-cursos)

Exercício 4

🧪 Fazendo um Code Review profissional

1

Abrir o PR do colega

Pull Requests → selecionar o PR que você foi marcado como reviewer → aba "Files changed" para ver as diferenças.

2

Verificar esses pontos no código

  • O código funciona? (abrir o arquivo e testar)
  • O nome dos arquivos está adequado?
  • A indentação está correta? (2 ou 4 espaços, consistente)
  • A mudança realmente resolve a Issue descrita?
  • A mensagem do commit está clara?
  • O PR tem descrição completa?
  • Há arquivos desnecessários (como .DS_Store)?
  • Há tags HTML semânticas (<header>, <main>, <footer>)?
3

Fazer comentários na linha do código

Passe o mouse sobre uma linha → clique no + azul → escreva um comentário específico. Use os exemplos abaixo como referência:

exemplos de comentários — do ruim ao bom
# ❌ Ruim — vago e desmotivador
"Isso está errado"
"Não gostei"

# ✅ Bom — específico, construtivo, com sugestão
"Sugiro usar a tag semântica <header> em vez de <div class='topo'>.
Representa melhor o cabeçalho para leitores de tela e SEO."

"Implementação correta do RN01. Para o RN02, faltou validar o campo 'data' — está listado no PDD mas não tem assert no test_validacao.py.
Pode adicionar: <a href='cursos.html'>Cursos</a> ?"

"[nit] Linha 14: há um espaço extra no final.
Pode deixar, mas se quisermos manter consistência no projeto..."

"O código resolve bem a Issue #1. Aprovado após a correção do link!"
4

Finalizar o review

Clique em "Review changes" → escolha uma das opções:

  • Comment — deixar observações sem bloquear nem aprovar
  • Approve — código está pronto para merge ✅
  • Request changes — há algo a corrigir antes do merge ❌

Regra da turma: todo PR deve ter pelo menos um comentário, mesmo que seja para aprovar e elogiar.

Exercício 5 — Solicitando e Fazendo Ajustes

PR não é "aceitar ou rejeitar" — é um diálogo

🎯
Objetivo

Entender que corrigir um PR não significa abrir um novo. Basta fazer mais um commit na mesma branch — o PR se atualiza automaticamente.

Exercício 5

🧪 Ciclo: sugestão → correção → re-review

Cenário didático

html — código antes da revisão
<!-- Código do Aluno A antes da revisão -->
<div class="topo">
  <h1>Meu Site</h1>
</div>
comentário do revisor no PR
"Sugiro usar a tag semântica <header> em vez de <div>,
pois representa melhor o cabeçalho para navegadores e SEO."
→ Status: "Request changes" ❌
1

Autor recebe o feedback e faz a correção localmente

bash — corrigir e atualizar o PR
# Confirmar que está na branch correta
git branch              # deve mostrar: * feature/cabecalho

# Fazer a correção no arquivo (no VS Code ou terminal)
# Antes: <div class="topo">
# Depois: <header class="topo">

git add index.html
git commit -m "fix: corrige cabeçalho usando tag semântica header"
git push
2

Verificar que o PR foi atualizado automaticamente

Abra o PR no GitHub. O novo commit aparece automaticamente na conversa. Não precisa abrir um novo PR!

3

Responder ao comentário do revisor

No GitHub, clique em "Resolve conversation" no comentário do revisor para indicar que foi corrigido. Ou escreva: "Corrigido no commit [hash]. Usei a tag <header> como sugerido."

4

Revisor faz o re-review

O revisor volta ao PR, verifica a correção e muda o status para Approve ✅ se estiver resolvido.

💡
Aprendizado central do exercício

Nunca abra um novo PR para corrigir o anterior. Faça o commit na mesma branch e o PR se atualiza. Um PR pode ter dezenas de commits — cada um respondendo a um feedback do review.

06

Exercício 6 — Merge do Pull Request

Integrando o código aprovado na main

📋 Issue ✓› 🌿 Branch ✓› 💾 Commits ✓› ⬆ Push ✓› 🔀 PR ✓› 👁 Review ✓› ✅ Merge› 🗑 Deletar
🎯
Objetivo

Entender os três tipos de merge do GitHub e quando usar cada um. Para iniciantes, começar com "Create a merge commit" e depois experimentar "Squash and merge".

Os três tipos de merge no GitHub

TipoO que fazQuando usar
Create a merge commitMantém todos os commits do PR + cria commit de mergePadrão — preserva histórico completo. Recomendado para iniciantes.
Squash and mergeUne todos os commits do PR em um único commit na mainQuando o PR tem commits "sujos" (wip, teste, ajuste). Histórico da main mais limpo.
Rebase and mergeReaplica commits linearmente, sem commit de merge extraPara histórico completamente linear. Requer commits bem organizados.
Exercício 6

🧪 Merge + limpeza de branch

1

Fazer o merge (após aprovação)

No PR aprovado, clique em "Merge pull request" → confirme. Comece com Create a merge commit.

Observe: a Issue vinculada (#1) é fechada automaticamente!

2

Deletar a branch após o merge

O GitHub mostra o botão "Delete branch" logo após o merge. Clique! Branch de feature não deve ficar aberta após ser integrada.

bash — limpar localmente também
# Sincronizar com o remoto
git switch main
git pull origin main        # baixar o merge que foi feito no GitHub

# Deletar a branch local
git branch -d feature/cabecalho

# Limpar referências de branches remotas deletadas
git fetch --prune

# Verificar que tudo está limpo
git branch                  # deve mostrar só: * main
git log --oneline -5        # ver o merge commit
3

Experimentar o Squash and Merge

No PR seguinte, use "Squash and merge" em vez de "Create a merge commit". Compare o histórico da main depois:

bash — comparar históricos
git log --oneline
# Com merge commit: vários commits do PR aparecem
# Com squash: apenas 1 commit limpo por PR
💡
Squash and Merge — por que ele existe

Durante o desenvolvimento de uma feature, é comum ter commits como "wip", "ajuste", "testando", "agora vai"... Esses commits não agregam ao histórico da main. O Squash os junta em um único commit limpo, como: feat: adiciona seção de cursos.

Exercício 7 — Protegendo a Branch main

Simulando um ambiente profissional real

🎯
Objetivo

Impedir que os alunos façam push direto na main. Em projetos reais, a main é protegida — o fluxo via PR se torna obrigatório, não opcional.

Exercício 7

🧪 Configurando Branch Protection Rules

1

Acessar as configurações

No repositório: Settings → Branches → Add branch protection rule

Em "Branch name pattern", digitar: main

2

Ativar as proteções

configurações recomendadas para a turma
✓ Require a pull request before merging
    Required approvals: 1
    ✓ Dismiss stale PR approvals on new commits

✓ Require status checks (se tiver CI configurado)
✓ Require conversation resolution before merging
✓ Restrict who can push to matching branches
    → incluir apenas o Tech Lead / professor

✓ Do not allow bypassing the above settings
3

Testar a proteção

Algum aluno deve tentar fazer push direto na main para ver o que acontece:

bash — testando a proteção
git switch main
echo "teste" >> README.md
git add . && git commit -m "teste direto na main"
git push origin main

# Resultado esperado:
remote: error: GH006: Protected branch update failed for refs/heads/main.
remote: error: Required pull request reviews must not be dismissed.
# ← O GitHub bloqueou! Agora o fluxo via PR é obrigatório.
💡
Aprendizado do exercício

O aluno percebe que, em projetos reais, ele não pode alterar a branch principal diretamente. O fluxo branch → commit → push → PR → review → merge deixa de ser uma sugestão e se torna a única forma de trabalhar.

Exercício 8 — Resolvendo Conflitos

O exercício mais importante da trilha

🎯
Objetivo

Entender que conflito não é erro — é o Git pedindo uma decisão quando duas pessoas editaram a mesma linha. Aprender a resolver de forma calma e comunicativa.

Exercício 8

🧪 Criando e resolvendo um conflito didático

Cenário — dois alunos editam o mesmo arquivo

situação
# Aluno A (em feature/cabecalho) escreve:
<h1>Bem-vindo ao Site da Turma</h1>

# Aluno B (em feature/secao-sobre) também edita index.html:
<h1>Projeto GitHub Colaborativo</h1>

# O PR do Aluno A é aprovado e mergeado primeiro.
# Quando o Aluno B tentar mergear: CONFLITO!

Opção A — Resolver no GitHub (conflitos simples)

1

GitHub detecta o conflito no PR

Na tela do PR do Aluno B aparece: "This branch has conflicts that must be resolved". Clique em "Resolve conflicts".

2

Ver os marcadores e decidir

html — arquivo com conflito
<<<<<<< feature/secao-sobre
<h1>Projeto GitHub Colaborativo</h1>        ← Aluno B
=======
<h1>Bem-vindo ao Site da Turma</h1>           ← Aluno A (main)
>>>>>>> main

# Decisão combinada com a equipe — remover os marcadores e deixar:
<h1>Bem-vindo ao Projeto GitHub Colaborativo da Turma</h1>
3

Confirmar a resolução

Após remover todos os marcadores e salvar a decisão, clique em "Mark as resolved" e depois "Commit merge".

Opção B — Resolver via terminal + VS Code (conflitos complexos)

bash — resolução local
# Na branch do Aluno B
git switch feature/secao-sobre

# Trazer as atualizações da main (onde o PR do A foi mergeado)
git pull origin main
# CONFLICT (content): Merge conflict in index.html

# Ver os arquivos em conflito
git status       # mostra "both modified: index.html"

# Abrir no VS Code para resolver visualmente
code index.html
# VS Code mostra botões: Accept Current | Accept Incoming | Accept Both | Compare
# Escolher a opção correta OU editar manualmente para uma terceira solução

# Após resolver e salvar:
git add index.html
git commit -m "merge: resolve conflito no título — combina versões dos dois alunos"
git push

# Verificar que não há mais marcadores
grep -r "<<<<<<<" .    # não deve retornar nada
💬
Comunicação resolve conflitos antes do Git

Quando dois alunos estão editando a mesma área do código, o melhor é combinar antecipadamente quem cuida de qual arquivo. A resolução técnica do conflito é simples — a parte humana (comunicação) é o verdadeiro aprendizado.

Exercício 9 — Atualizando Branch Desatualizada

O que fazer quando colegas avançaram e você ficou para trás

🎯
Objetivo

Entender que uma branch pode ficar desatualizada em relação à main conforme outros PRs são mergeados. Aprender a trazer as atualizações de forma segura.

Exercício 9

🧪 Simulando branch antiga e atualizando

Cenário

A main recebeu 3 novos merges enquanto você trabalhava na sua branch. Seu PR agora mostra: "This branch is out-of-date with the base branch."

1

Verificar o quão desatualizada está sua branch

bash
git fetch origin
git log --oneline HEAD..origin/main   # commits que existem na main mas não na sua branch
2

Trazer as atualizações da main para a sua branch

bash — atualizar a branch (opção recomendada para iniciantes)
# Garantir que está na sua branch
git switch feature/secao-cursos

# Atualizar a main local
git switch main && git pull

# Voltar para sua branch e trazer as atualizações da main
git switch feature/secao-cursos
git merge main           # integra o que há na main na sua branch

# Se houver conflitos, resolvê-los (como no Ex.8)
# Depois:
git push                  # atualizar o PR automaticamente
💡
Rotina preventiva

Execute toda manhã antes de começar a trabalhar: git switch main && git pull && git switch feature/sua-branch && git merge main. Isso evita que a branch fique muito desatualizada e reduz conflitos acumulados.

Exercício 10 — Fork e Contribuição Externa

O modelo usado em projetos open source

🎯
Objetivo

Aprender o fluxo de fork: quando você não tem permissão no repositório original, você cria sua própria cópia (fork) e contribui via PR. Preparação para colaboração em projetos open source.

Exercício 10

🧪 Contribuindo para o repositório do professor

1

Professor cria o repositório-modelo

2

Alunos fazem fork do repositório

No GitHub, acessar o repositório do professor → clicar em Fork (canto superior direito) → confirmar. Agora cada aluno tem sua cópia em github.com/SEU_USUARIO/projeto-modelo-html.

3

Clonar o fork e adicionar o nome

bash — fluxo de fork
# 1. Clonar SEU fork (não o do professor)
git clone https://github.com/SEU_USUARIO/projeto-modelo-html.git
cd projeto-modelo-html

# 2. Adicionar o repositório original como "upstream"
git remote add upstream https://github.com/PROFESSOR/projeto-modelo-html.git
git remote -v
# origin   = seu fork (você tem permissão total)
# upstream = repositório do professor (só leitura)

# 3. Criar branch para a sua contribuição
git switch -c docs/adiciona-nome

# 4. Adicionar seu nome ao arquivo
echo "- [Seu Nome](https://github.com/SEU_USUARIO)" >> participantes.md

# 5. Commitar e enviar para o SEU fork
git add participantes.md
git commit -m "docs: adiciona [Seu Nome] à lista de participantes"
git push -u origin docs/adiciona-nome

# 6. No GitHub, abrir PR do seu fork para o repositório do professor
# base repository: PROFESSOR/projeto-modelo-html   branch: main
# head repository: SEU_USUARIO/projeto-modelo-html  branch: docs/adiciona-nome
4

Professor aprova e mergeia os PRs

O professor revisa cada PR e mergeia para o repositório original. Os alunos veem suas contribuições aparecerem no repositório do professor!

5

Sincronizar o fork com o repositório original

bash — manter fork atualizado
git fetch upstream
git switch main
git merge upstream/main     # seu fork agora tem as contribuições dos colegas
git push origin main        # atualizar o fork no GitHub também

Exercício 11 — Pull Requests no VS Code

Gerenciando PRs sem sair do editor

🎯
Objetivo

Usar a extensão GitHub Pull Requests and Issues para visualizar, revisar e responder a PRs diretamente no VS Code — o mesmo ambiente onde você escreve código.

Exercício 11

🧪 Configurando e usando a extensão

1

Instalar a extensão

No VS Code: Extensions (Ctrl+Shift+X) → buscar "GitHub Pull Requests and Issues" → Install. Publicada pelo próprio GitHub.

2

Fazer login no GitHub pelo VS Code

Após instalar, clique no ícone do GitHub na barra lateral → "Sign in" → autorize o acesso. O VS Code agora tem acesso aos seus repositórios e PRs.

3

Visualizar PRs abertos

Na barra lateral do VS Code, aparece o ícone do GitHub Pull Requests. Clique para ver:

  • PRs que você criou
  • PRs que você precisa revisar
  • Todos os PRs do repositório
4

Fazer review de um PR no VS Code

Clique em um PR → "Checkout" para ver o código no contexto certo → clique no arquivo para ver as mudanças → clique em uma linha para comentar diretamente. Tudo isso sem abrir o navegador!

5

Ver Issues no VS Code

Na aba de Issues (mesma extensão), você pode criar Issues, atribuí-las e criar branches vinculadas diretamente pelo VS Code — sem sair do editor.

💡
Por que isso importa

Profissionais passam horas nos seus editores. Ter acesso ao fluxo de PR sem precisar alternar entre VS Code e navegador aumenta significativamente a produtividade e reduz contexto-switching.

Criar um checklist padrão que todos os PRs do repositório devem incluir. Isso cria disciplina coletiva e reduz erros óbvios antes da revisão.

markdown — .github/pull_request_template.md

Exercício 13 — Boas Mensagens de Commit

O histórico do projeto é a documentação mais honesta que existe

🎯
Objetivo

Aprender a escrever mensagens de commit que comunicam intenção, não apenas o que foi feito. Um bom histórico permite entender o projeto sem ler uma linha de código.

Exercício 13

🧪 Reescrevendo mensagens ruins

Reescreva as mensagens abaixo seguindo o padrão Conventional Commits:

Formato: tipo: descrição imperativa sem ponto final

Mensagem ruimContextoMensagem corrigida
testeVerificou se o menu apareciafeat: adiciona menu de navegação ao cabeçalho
ajusteCorrigiu alinhamento do headerstyle: corrige alinhamento horizontal do cabeçalho
bugCorrigiu link quebrado na navfix: corrige link quebrado na navegação para Cursos
coisasAdicionou seção de cursosfeat: adiciona seção de cursos à página inicial
finalAtualizou o READMEdocs: atualiza README com instruções de instalação
agora vaiCorrigiu tag div para headerfix: substitui div por tag semântica header

Atividade — reescrever em dupla

mensagens para reescrever
mudei o css           → Qual tipo? O que mudou? Por quê?
atualização           → De quê? Para quê?
não sei               → Jamais commitar sem saber o que foi feito
fix                   → Fix de quê?
salvo                 → O Git já salva. O commit precisa descrever o que mudou.
semana 3              → Histórico não é diário de bordo, é registro de intenção
Implementa RN01 (estrutura) e RN02 (campos obrigatórios) em src/validacao.py. Testes em tests/test_validacao.py com cobertura de 87%.
→ Muito longo. Regra: máximo 72 caracteres. Detalhe no corpo se necessário.
💡
Teste mental antes de commitar

Complete a frase: "Se aplicado, este commit vai ___________". A resposta é o que vai depois do tipo. Exemplo: "vai adicionar o menu de navegação ao cabeçalho" → feat: adiciona menu de navegação ao cabeçalho

Dinâmica — Simulando uma Equipe Real

Papéis definidos, entrega real, fluxo completo

Esta dinâmica simula um ambiente profissional com papéis definidos. Cada aluno assume uma responsabilidade diferente durante o desenvolvimento de uma landing page para um curso de programação.

Papéis da equipe

👑 Product Owner

Define as tarefas

Cria as Issues com requisitos claros, define prioridades, aceita ou rejeita entregas com base nos critérios de aceite.

💻 Dev 1

Implementa o header

Cabeçalho com logo, navegação e hero section. Branch: feature/header

💻 Dev 2

Implementa o conteúdo

Seções de benefícios, grade curricular e depoimentos. Branch: feature/conteudo

💻 Dev 3

Implementa o formulário

Gerador de relatório .xlsx. Branch: feature/relatorio

👁 Revisor

Analisa os PRs

Revisa código, verifica critérios de aceite, faz comentários construtivos e aprova ou solicita mudanças.

🔀 Integrador

Faz o merge

Realiza o merge dos PRs aprovados, resolve conflitos que surgirem na integração, mantém a main estável.

Regras da dinâmica

  • O PO cria todas as Issues antes de qualquer dev começar
  • Cada dev cria exatamente uma branch para sua feature
  • Cada dev abre exatamente um PR quando terminar
  • O revisor deve deixar pelo menos 2 comentários em cada PR
  • O autor do PR deve responder a todos os comentários antes do merge
  • O integrador só faz merge após a aprovação do revisor
  • Ninguém faz push direto na main

Entrega final da dinâmica

Cada grupo apresenta para a turma:

o que apresentar
1. Histórico de commits
git log --oneline --graph

2. Branches criadas e mergeadas
git branch -a

3. Issues fechadas
# Aba Issues → Closed

4. Pull Requests aceitos
# Aba Pull Requests → Closed

5. O site funcionando no navegador
🗣️
Perguntas para a apresentação

• Qual foi o maior conflito que encontraram?
• O que fariam diferente se repetissem?
• Qual papel foi mais desafiador?
• O que aprenderam que não sabiam antes?

Por que criar uma Release?

A Release é um marco rastreável — no projeto da LG Electronics, cada release corresponde a um conjunto de regras do PDD testadas e validadas. A tag v0.1.0 é a evidência de entrega exigida pelo Convênio 005/2025 e pode ser apresentada na banca de avaliação.
